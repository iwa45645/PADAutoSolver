# 開発再評価・整理（2026-10-05）

本書前半はdev41/B19後停止時点の評価です。続行後の反映状況を末尾に追記し、当初評価を履歴として保持します。現在はdev52で今回のB22クリアと報酬まで確認済みです。

## 評価（基準時点）

現在のPADAutoSolverは、利用者の固定編成・実測端末・既知の出現分岐に合わせて、裏魔門のB19までを個別に通過した開発版です。全22階を同じAPKで新規潜入からクリアする製品状態には達していません。到達階数から完成率を計算することもできません。

最も優先すべきなのは、階ごとに増えた「操作を送ったか」「ゲームに反映されたか」「どこから再開できるか」の例外処理を整理することです。その上で残る階を実装し、最終版で全階を通して確認します。今回の再評価は資料の整理であり、下記の修正を実装済みと扱いません。

コード基準点：`d084cf38c4dc22b2c2d61c95774b22f04d9e2bf4`、0.4.0-dev41 / versionCode44。対象端末の実測画面は1220×2712です。最後の実機観測はB19突破後のB20入口で停止した2026-10-05 08:34:03 JST。今回は端末を操作していません。

## 維持する成果

- 画面取得・スキル操作・パズル・進行を本体で行う構成と、停止・モード分離。
- 同じpackageNameと固定署名、鍵をコミットしない運用、Actionsのビルド検証。
- 日付別の実機証跡、保存された盤面・スキル情報・再開地点。
- B2の指示別パズル、実測ルーレットの色の組合せ検算、遅延や超根性への個別対応。
- 不明な画面で停止し、画像取得やビルド成功を全階攻略の成功と混同しない方針。

固定編成を再選定したり、BOX全件の確定同定を攻略の前提に戻したりしません。潜入前は助っ人ミオンだけを確認する利用者条件を保持します。売却は別モードで、合計MP30以外は停止する条件を保持します。

## 修正の優先順位

P0は新しい階へ広げる前に対処する項目、P1は全階攻略・通し検証の成立に必要な項目、P2は正しさを確立した後の改善です。

| ID | 優先 | 問題と根拠 | 対処 |
| --- | --- | --- | --- |
| R1 | P0 | UraProgressControllerが操作送信前に消費済みのphase/opを保存する。AutoPuzzleServiceは送信直前に前面・接続・世代・フレーム鮮度を再確認して送信を取りやめる場合がある。B15では未反映操作の復旧例外が必要になった | 準備・送信・Android応答・ゲーム結果確認を分離し、結果不明状態も保存する |
| R2 | P0 | UraProgressControllerの攻撃後phase10は18秒待機を基準にroundを進める。B15などの例外はあるが、全階共通の「実ターンが進んだ」確認ではない | CD・敵のカウンター・階層・盤面変化等の証拠でターンを確定。時間は上限にする |
| R3 | P0 | B1・B3・B5、B6/7の標準目的にwaterAndHealが残り、B4のRoulettePlanも水2セット＋回復が中心。B8以降のesperMionAndHealとは異なる | 通常攻撃では水T字＋水2セット＋回復を共通条件にする。B2指示・充填・暗闇処理等は明示的な例外にする |
| R4 | P1 | Controllerごとに再開形式・数値phaseが異なる。画像とJSONを別々に書き、共通schemaVersion・画像hash・一括確定がない | 共通チェックポイント、セッションと版、画像との対応、原子的な確定と破損検知を導入する |
| R5 | P1 | 1220×2712のROI、既知の敵画像、OCR補正に依存。再開時の肖像照合や明るさ差で停止する条件がある | 対象領域ごとに照合を正規化し、適用端末・画像出典・不明理由を記録。根拠なく閾値を緩めない |
| R6 | P1 | UraProgressPolicyの戦略はJava配列で、ura_shura_profile.jsonを全階攻略の実行設定として読み込む経路がない | 共通操作を先に抽出し、戦略・認識・実行を段階的に分離。最初から全面書換えしない |
| R7 | P1 | B20〜B22のscriptがnull。最終クリア・結果画面までの裏魔門の完了条件も未検証 | 続行指示後に現画面を再取得し、残る階とクリア結果を実装・実機確認する |

| R9 | P2 | スキル前後の4秒hold、攻撃後18秒、MENU往復、探索時間と静止待ちが累積する | 結果が確認できたら待機を早期終了。入力を速めるだけの変更は先行しない |

R1のAndroid応答はGesture callbackの完了を意味し、ゲーム側でスキル・パズルが成立した証明ではありません。送信直前の条件確認と二重発動の防止は維持しながら、未送信と結果不明を区別します。

R3は実際に早い階を通過できたことを否定するものではありません。しかし水2セット＋回復だけを満たす探索では、エスパーの水T字条件まで保証できません。「早い階でも両リーダーの火力・軽減を常に発動できる」とは評価しません。

R4の書込み中断・画像/JSON不整合はソースから分かる設計上のリスクであり、今回新たに端末で障害を再現した結果ではありません。R10のassets容量はAPK容量の一因ですが、APK全体の内訳を解析した結果ではありません。

## 続行後の反映（2026-10-07、開発再開試験）

同日記録の修正はR5/R9を中心に実機停止から検証している。R3はdev53で標準攻撃を共通化したが、単一最終APK通しは未達。R5では毒・強化色・コンボ・7×6・鍵表示の実画像を、別時点の独立fixtureで確認し、分類閾値.07/.035を維持。HP色や数字点滅・階層11字形も、数値を推測せず実画素と字形で検査している。

R9はtooltip証拠の保存と送信を異なる新鮮フレームへ分け、1,500msの送信前鮮度制約を維持。経路TTL15秒を認識処理中にまたいだ場合は、未送信の最新盤面から再探索する。条件一致が表示の点滅で途切れるケースと60秒watchdogは残り、全処理の安定化完了とは扱わない。

R10はorb bitmapを48×48画素取得後に解放した。B10の異なる処理phaseでPSS減少を観測したが、統制benchmarkでも保存容量管理の完了でもない。pixel cacheと非orbテンプレートは保持。R1/R2/R4の共通化・PNG/JSON一体hash・全中断地点、R6/R8、全敵分岐、通常周回/売却回帰も未完了。

実機の各階突破は更新・停止・再開を含む。fresh試行3回・無中断クリア0を維持し、同一最終APK20回/19無中断クリア/誤操作0が成立するまでstable Releaseとして公開しない。最新の階層・版・未送信操作は[現在の状況](implementation-status.md)と[10/7記録](stability-validation-2026-10-07.md)を優先する。
